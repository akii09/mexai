## The three context layers

mexai maintains three Markdown files per project, each serving a distinct purpose:

### Layer 1 — Project context (`context.md`)

The "who you are and what you're doing" layer. Contains:

- **Identity** — a paragraph describing the project's purpose, audience, and goals
- **Current state** — what's being worked on right now
- **Open threads** — in-progress work items and questions
- **Decisions** — architectural and design decisions with rationale and date

This is the layer AI agents read most frequently. It answers: *"What is this project and where is it right now?"*

### Layer 2 — Codebase map (`codebase.md`)

The "how the code is organised" layer. Contains:

- **Key files** — the most important files and their purposes
- **Conventions** — naming conventions, file organisation rules
- **Structure** — directory tree with annotations
- **Patterns** — recurring code patterns agents should follow
- **Do Not Touch** — files that must not be modified without explicit approval

Generated by `mexai map` from a static scan. No AI, no API calls — pure filesystem analysis.

### Layer 3 — Agent rules (`rules.md`)

The "how to write code here" layer. Contains:

- Code quality rules
- Security rules (no eval, validate external input, etc.)
- Consistency rules (naming, imports, error handling)
- Review gates (tests must pass, no new lint warnings, etc.)

Rules are never truncated — they fit in full or you get a budget warning.

## The pending diff model

mexai never automatically applies context changes. Every change goes through a **staged → reviewed → committed** cycle:

```
AI agent calls context_save
         │
         ▼
    pending-diff.json  ←── staged (not committed)
         │
    mexai diff         ←── you review what changed
         │
    mexai commit       ←── you apply it
         │
         ▼
    context.md updated, git commit created
```

This means:
- You always review before anything is written to your context
- If the AI staged something wrong, `mexai diff --discard` throws it away
- Multiple saves before a commit are merged correctly (decisions append, current state last-write-wins)

The `mexai apply` command combines stage + commit in one step for when you trust the change.

## Project state machine

Every project is in one of three states:

| State | Meaning |
|---|---|
| `● CLEAN` | No pending diff, store git is clean |
| `● STAGED` | A pending diff exists, waiting for `mexai commit` |
| `● DIRTY` | Store git has uncommitted changes (e.g. after `mexai edit`) |

Check with `mexai status` or `mexai status --json`.

## Token budget

mexai injects context within a configurable token ceiling (default: 700 tokens total across all three layers). Each layer has a priority-based truncation strategy:

| Layer | Truncation strategy |
|---|---|
| Context | Oldest decisions removed first; newest threads kept |
| Codebase | Deepest directory levels removed first; key files never truncated |
| Rules | Never truncated — budget warning if over limit |

The injection order is: **rules → context → codebase** (most important first).

## Project detection

mexai uses a `mexai.json` file in your project root for reliable auto-detection. When you run any command from inside a registered project, mexai walks up the directory tree looking for `mexai.json` — exactly like how `git` finds `.git`.

Resolution chain (highest priority first):
1. Explicit `--project <slug>` flag
2. `mexai.json` walk-up from current directory
3. Interactive picker (TTY only)
4. Error with helpful message

## Git-backed store

Each project store is a standalone git repository at `~/.mexai/projects/<slug>/`. Every `mexai commit` creates a git commit, giving you a full history of your context changes.

Use `mexai log` to see the history and `mexai restore <hash>` to roll back to any previous state.

## MCP server

`mexai serve` starts a Model Context Protocol server over stdio. AI editors connect to it via their MCP config and call five tools:

- `context_read` — read all context layers (auto-resolves project from workspace path)
- `context_save` — stage a context change for review
- `codebase_read` — read the codebase map
- `rules_read` — read agent rules
- `context_list` — list all registered projects

The MCP server is a thin adapter over `@mexai/core`. All business logic lives in core.
